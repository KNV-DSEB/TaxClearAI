## 2. Architecture Rules — MVC + Module Pattern

### MVC + Module pattern (NON-NEGOTIABLE)

```
Request → Controller/Router → Service → Repository → Model/Entity
```

- **Controller/Router**: ONLY receive request, validate input shape, call service, return response. NEVER contain business logic, NEVER query DB, NEVER import ORM/DB session directly.
- **Service**: ALL business logic lives here. MAY call multiple repositories and orchestrate operations. NEVER import ORM models to query DB directly. NEVER duplicate logic that exists in another service — compose instead.
- **Repository**: The ONLY layer allowed to query the DB. Returns domain objects, not raw DB rows. NEVER contains business logic or validation. Lives inside its feature's own `modules/[feature]/` folder, next to the controller/service — NOT in a shared top-level `repositories/` folder.
- **Model/Entity**: Data definition ONLY (ORM decorators/columns). NEVER contains business logic methods. Stays a separate top-level folder (`entities/` or `models/`).

This chain applies to every framework this project uses. Concrete file-naming and violation examples for your specific backend framework are in `backend-mvc.md` and, if this project has a frontend, in `frontend-structure.md`.

### Module structure rule

Each business domain = one module folder. New feature = new module folder. NEVER add unrelated functionality into an existing module. Do not add or remove top-level folders (`modules/`, `core/`, the model/entity folder, etc.) — the folder shape is a hard contract, not a suggestion.

## 4. Backend Structure — FastAPI

### Tech stack (Backend)
- **Framework**: FastAPI 0.115+ · **Language**: Python 3.12+
- **ORM/DB**: SQLAlchemy (async) + PostgreSQL, Alembic for migrations
- **Validation**: Pydantic v2 models for every request/response body
- **Auth**: `python-jose` (JWT) + `passlib[bcrypt]`
- **Package manager**: poetry (or pip + `requirements.txt` for `tool-script`)

### Module structure

```
modules/[feature]/
  ├── __init__.py
  ├── router.py         ← APIRouter — Controller in MVC, e.g. @router.post("/login")
  ├── service.py         ← [Feature]Service class — business logic
  ├── repository.py      ← ONLY layer allowed to run session.execute()
  ├── schemas.py         ← Pydantic request/response models (DTOs)
  └── dependencies.py    ← Depends() functions: get_current_user, require_admin
```

The repository lives inside its feature's module, not in a shared top-level `repositories/` folder. `models/` (the SQLAlchemy ORM classes) stays a separate top-level folder.

Cross-cutting concerns live in `core/`: `config.py` (pydantic-settings), `database.py` (async engine/session), `security.py` (JWT + hashing), `exceptions.py`, `middleware.py`, `logging.py`.

### Violation examples (AI will refuse to generate these)

```python
# ✗ WRONG – router.py querying the DB and doing business logic directly
@router.post("/login")
async def login(data: LoginRequest, db: AsyncSession = Depends(get_db)):
    user = await db.execute(select(User).where(User.email == data.email))
    if user.is_active and user.role == "admin":
        hashed = bcrypt.hash(data.password)

# ✓ CORRECT – router.py only delegates
@router.post("/login")
async def login(data: LoginRequest, db: AsyncSession = Depends(get_db)):
    result = await auth_service.login(data, db)
    return TokenResponse(**result)
```

- `router.py` NEVER calls `db.execute()`/`session.execute()` directly — that belongs in `repository.py`.
- `router.py` NEVER contains conditionals expressing business rules.
- `schemas.py` classes NEVER have methods containing business logic — Pydantic shape definitions only.

## 5. Frontend Structure

### Tech stack (Frontend)
- **Framework**: nextjs — Next.js 15 App Router | React 18 + Vite | Vue 3 + Vite
- **Styling**: Tailwind CSS · **State**: Zustand (React/Next) or Pinia (Vue)
- **Package manager**: pnpm

### Naming conventions

- Components: `PascalCase/PascalCase.tsx` (or `.vue`)
- Hooks: `use[Name].ts` (React/Next) · Composables: `use[Name].ts` (Vue)
- Services: `[name].service.ts` · Store files: `[name].store.ts` (`[name].store.ts` → Pinia store for Vue)

### Structure rule

```
src/
  ├── components/
  │   ├── common/       ← reusable UI (Button, Input, Modal — no business logic)
  │   └── features/     ← feature-specific components
  ├── hooks/ (or composables/ for Vue)
  ├── services/         ← ALL API calls go here, nowhere else
  ├── store/
  ├── types/
  └── utils/
```

- Every network call goes through a `services/*.service.ts` file. Components/pages NEVER call `fetch`/`axios` directly.
- `services/api.client.ts` is the ONE place that reads the API base URL from environment variables.

### Additional rules when this project is `app-fe-only`

`app-fe-only` means the backend already exists in a separate, reusable project — this project owns no data layer.

- NEVER create `backend/`, `models/`, or `repositories/` folders — there is no local backend to scaffold.
- `types/api.types.ts` must match the external API's real contract. If the contract changes, update the types first — never guess a field's shape.
- The external API base URL lives ONLY in `.env` (`NEXT_PUBLIC_API_URL` for Next.js, `VITE_API_URL` for Vite-based FE) and is read exclusively by `services/api.client.ts`.

### Violation examples

```typescript
// ✗ WRONG – component calling fetch directly
function UserProfile() {

    fetch(`${process.env.NEXT_PUBLIC_API_URL}/users/me`).then(...);
  }, []);
}

// ✓ CORRECT – component calls a service
function UserProfile() {
  useEffect(() => {
    usersService.getMe().then(...);
  }, []);
}
```

## 6. Security Rules

- **Secrets**: NEVER hardcode secrets, API keys, tokens, or passwords. ALWAYS use environment variables. `.env` is gitignored; `.env.example` lists required vars WITHOUT values.
- **Input validation**: ALWAYS validate ALL user input at the Controller/Router level (class-validator DTOs, Zod, or Pydantic models depending on stack). Sanitize strings to prevent XSS. Validate file uploads: extension whitelist + size limit.
- **Auth**: JWT short-lived access token (15min) + refresh token (7d). ALWAYS check authentication before business logic. Use RBAC via middleware/guards. NEVER trust client-sent user IDs — always use token claims.
- **Database**: ALWAYS use parameterized queries / ORM, NEVER raw string interpolation. Connection pool with sensible limits. DB user has minimum required permissions.
- **API**: Rate limiting on all public endpoints. CORS configured explicitly — no wildcard in production. HTTPS enforced in production. Security headers on by default.

## 7. Code Style Rules

- NEVER swallow exceptions silently. ALWAYS log errors with context (request ID, user ID if available) — see the Logging rule.
- Return RFC 7807 Problem Details format for API errors (`type`, `title`, `status`, `detail`, `instance`).
- ALWAYS use async/await, never raw callbacks. ALWAYS handle Promise rejections. TypeScript: annotate async return types. Python: `async def` + `await` throughout FastAPI.
- Comment WHY, not WHAT. Public functions/methods get a one-line docstring/JSDoc only when the signature alone doesn't explain intent.

## 12. Clean Code & Simplicity

- Small, single-purpose functions; indent depth max 3 levels; name things clearly rather than cleverly.
- No dead code: no unused exports, no commented-out code, delete orphaned imports/files in the same change that made them orphaned.
- No copy-pasted logic — duplicated in ≥2 places → extract a shared function.
- No new dependency when a library already in the stack (the ORM, the validation library, the HTTP client already chosen) can do the job.
- No speculative abstraction (YAGNI) — only extract a shared layer once there are ≥2 real call sites, not "for later".

## 13. Logging

- Structured logs only (JSON), never a bare free-text `console.log`/`print` in a production code path — use the project's logger (Winston/Pino for Node, `logging`/`structlog` for Python).
- Every log entry gets the correct level: `debug` (dev-only diagnostics), `info` (normal operational events), `warn` (unexpected but not broken), `error` (a single operation failed), never log-and-continue silently on something that should be an `error`.
- Every log carries context: a correlation/request ID that propagates across the whole request lifecycle, plus the relevant entity ID (user ID, order ID, etc.) — a log line must be useful in isolation.
- NEVER log secrets, passwords, tokens, full card numbers, or raw PII (emails/phone numbers) — mask or omit them.

## 14. API Design

- Nouns, not verbs: `/users` not `/getUsers`. Plural collections. Nested resources for relationships (`/users/{id}/orders`). kebab-case in paths, camelCase in JSON bodies.
- Version in the URL (`/api/v1/...`) — never a breaking change on an existing version.
- Respect HTTP method semantics: `GET` never mutates state; `PUT` replaces the whole resource; `PATCH` partially updates; `POST` on a collection returns `201 Created` + `Location`; `DELETE` returns `204 No Content`.
- One consistent response envelope and one consistent error format (RFC 7807 — see the Code Style rule) across every endpoint. Never remove/rename a field in an existing response; add new fields as optional.
- Pagination on every list endpoint (see the Performance rule) — never return an unbounded list.

## 15. Code Review Checklist

Before suggesting a PR is ready, or when asked to review a diff, check:

1. **Layer boundaries** (see the Architecture rule) — Controller/Router only parses input and delegates; Service never queries the DB/ORM directly; Repository has no business logic; Model/Entity has no methods with logic. Frontend: every API call goes through `services/*.service.ts`, never inline `fetch`/`axios` in a component.
2. **Folder placement** — genuinely new feature → new `modules/<feature>/` (or `components/<feature>/`) folder; anything added to an unrelated existing module gets flagged. No new top-level folders outside the Architecture rule's contract.
3. **Security** (see the Security rule) — no hardcoded secret; every user input validated at the Controller/Router level; no raw string interpolation into a query; nothing trusts a client-sent user ID over the token's claims.
4. **Error handling & async** (see the Code Style rule) — no swallowed exception, no unhandled Promise rejection, no callback-style async mixed into an async/await codebase.
5. **Tests** — new business logic has a corresponding unit test; unit tests mock external services instead of calling them for real.
6. **Lint/type-check/tests pass**, no debug logs or commented-out code in the diff, `.env.example` updated if new env vars were added, a migration file was added if the DB schema changed.

Do not flag stylistic preferences that ESLint/Prettier/ruff/black would already catch — this checklist is for the architectural judgment calls automated formatting and linting cannot make.

## 17. Workflow Contract

Applies to every code change, regardless of which AI tool is making it:

1. **Explain the design before writing code** for a non-trivial step — state the approach and why, before generating the diff.
2. **Verify before calling a step done** — run build/type-check/lint/test for the exact workspace you touched (e.g. `backend` vs `frontend`) after every edit. Never report a step complete without having actually run the check.
3. **Remove dead code created by the same change** — orphaned imports, now-unused functions/files — in the same change, not a follow-up.
4. **Transient failures** (network timeout, flaky test, a temporary lock file): retry exactly once. If it still fails, stop and report what was tried instead of silently skipping the check or bypassing it (no `--no-verify`, no `--force`).
5. **Report honestly** — list exactly which files changed, which commands were run, and their real output (including failures and what wasn't verified yet). Never say "done" when the build/tests haven't actually been run or are currently failing.
